# Evidence correction concurrency safeguards — 2026-11-08

Correction saves now serialize within the current application session. They capture the workspace, case, evidence snapshot, viewer request, review-state object and quarantine-history reference, and check that context before writing the correction pointer and before publishing the review pointer. Closing or changing the viewer, starting new intake, switching cases, or completing another review-state change causes a stale save to stop at the next check. The correction text area is disabled while saving; editing afterward clears the previous success message.

If a correction pointer write has been attempted and a later step fails or detects changed context, the UI warns that the correction or review pointer may already have been saved and directs the user to reopen the case and inspect saved state. An immutable correction may also remain without a pointer if the context changes before pointer publication. Closing the viewer can remove the screen that would show the warning. These are same-session optimistic checks, not an atomic multi-file transaction, a cross-window lock, cancellation of an in-progress filesystem write, or reviewer authentication. Review operations that are concurrently in flight but have not yet updated in-memory state may not be detected. A formal concurrency and recovery policy remains necessary before real-data use.

Synthetic Chromium tests covered closing during a delayed immutable write, changing a classification during a delayed pointer write, subsequent retry, regular viewer and correction behavior, and a normal correction save from an isolated built `file://` artifact with HTTP blocked. The workspace was simulated. Typecheck, lint, format, schema and contract checks passed; the isolated single-file build and verifier passed. Native filesystem behavior, independent execution, office security controls, and human approvals were not tested. The existing Vite browser-externalization warning remains.
