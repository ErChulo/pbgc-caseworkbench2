# Local population row inspection — 2026-11-06

For an approved workbook population candidate, the population review panel now offers an explicit, temporary local row inspection. The user supplies the exact sheet name, one-based data row, and up to 50 explicit generic-field, uppercase-column and row-one-header bindings; the app does not choose a participant or infer mappings. Before showing a row, it checks current case, workspace, snapshot and review freshness; compares current and replayed review history; reopens the preserved source workbook from the case snapshot; verifies bytes, passive inspection, candidate, profile and decision consistency; and projects the selected row. A mismatch, formula source, missing or blank cell remains visible as its own state; formula cached values are not displayed as participant values. The UI identifies the profile and record hashes, reports actual value states, escapes display control characters, and explicitly says the view is not selection authorization or routing approval.

The screen warns that the view can contain participant data and requires appropriate local case-data and screen controls. Values are not logged or persisted by this feature. Editing a selection, clearing the view, changing the review/build context, or switching cases removes displayed results and prevents stale in-flight results from publishing. Clear also resets the row, sheet and bindings. Source bytes may still change outside this browser after inspection: the check is not a cross-window transaction or durable authorization. The source hash and local decision do not authenticate reviewer identity, evidence eligibility, or actuarial authority.

The domain row projector now snapshots its inputs before hashing and freezes its returned record; caller mutations cannot change the row, bindings or review decision after the profile digest is computed. Non-cloneable inputs fail closed. This is a review aid, **not production workbook routing**: the I/B routing and scenario-target blockers remain. Bindings are user assertions, not approved mappings or Data Dictionary validation; no population values are routed to a generated workbook and no release readiness is conferred. Existing tabular population candidates do not use this workbook-only view. The current profile hash uses locale-sensitive ordering for defined names; a governed, versioned hash-policy migration is needed before claiming cross-environment stability, rather than silently changing existing approval hashes.
