# Evidence viewer and candidate byte binding — 2026-11-07

The evidence viewer and catalog candidate reconstruction now copy a bounded source object once and hash that exact copy before displaying or parsing it. Previously each hashed a reader and then read it again, so a changing source could produce different bytes after verification. The viewer keeps its existing 128 MiB cap; candidate reconstruction now uses the 32 MiB intake inspection cap. Size, chunk offsets, lengths, end markers and SHA-256 must match. No result is published from a failed check.

Viewer requests now have a sequence and case/workspace/snapshot guard. Starting another view, closing the viewer, starting a new intake, or resetting the case invalidates pending viewer responses. A completed correction save no longer reopens an old viewer after the reviewer closes it or selects another artifact. This does not cancel a correction write already underway, make correction and review writes transactional, authenticate a reviewer, establish source authority, or protect against later external modification of the workspace. Other workspace operations still require their own freshness and integrity checks.

Synthetic unit tests cover exact copied-byte hashing, malformed reads and size limits. Seven Chromium tests covered viewer and correction flows and selection/close races on the development origin; an additional built-file test opened a synthetic text source with HTTP blocked and an in-memory workspace. Typecheck, lint, format, schema and contract checks and an isolated single-file build/verifier passed. The full suite reported 1,195 passing tests, four skipped and one failed Data Dictionary suite caused by missing approved LFS bytes. The existing browser-externalized Node module warning remains. No native office workspace, real data, external workbook execution or human approval was tested.
