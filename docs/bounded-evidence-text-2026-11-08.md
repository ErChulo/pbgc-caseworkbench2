# Bounded evidence text records — 2026-11-08

Extraction and correction pointer reads are now limited to 64 KiB, and their JSON records to 64 MiB, using strict chunk accounting. Existing records inspected before reuse follow the same bound. New serialized records are checked against the same record limit, and new corrected text is limited to 8,388,608 UTF-16 code units before screening and classification. These are local resource limits, not approved business limits. The viewer explains the correction limit; records above the limits are not truncated and require an approved alternative workflow.

A newly created extraction or correction is reread and compared byte-for-byte before its current pointer is published. If readback fails, the pointer is not published; an unreferenced record may remain. An extraction failure during intake blocks further case actions and warns of possible partial writes. When the viewer cannot verify existing text metadata it still permits viewing verified original bytes, but does not display or permit correction of the unverified extraction. Restoration and candidate processing also fail closed where these reads fail.

Synthetic Chromium tests rejected oversized extraction and correction pointers and records, and simulated tampering between each new record write and readback. The built `file://` test rejected an oversized pointer with HTTP blocked; existing correction concurrency, viewer and synthetic production tests passed. Tests used an in-memory workspace. Typecheck, lint, formatting, schemas, contracts, isolated build and verifier passed. The full suite had 1,201 passed, four skipped and one Data Dictionary suite failure because approved Git LFS bytes are missing.

A successful readback does not prevent later changes or establish authenticity, derivation, reviewer authority, or an atomic cross-window transaction. An orphan or partial write can remain. The limits do not bound all parser, serialization, matching or memory work before record creation and do not cover all workspace metadata. The native office filesystem, real data, external execution and actuarial approval remain unverified. Vite retains its browser-externalized Node warning, and the app is not ready for real-data office testing.
