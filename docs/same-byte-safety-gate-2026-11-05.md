# Same-byte safety findings and eligibility

## Problem and change

A same-byte re-submission can have different contextual findings, such as a script-capable filename. The prior intake path could add a new quarantine item while retaining an existing eligible projection for the same hash. A previous eligibility approval could therefore remain visible as eligible despite a new safety hold.

The intake queue now retains the union of the previously observed and newly observed finding IDs. Eligibility is constrained by the current finding set: an effective same-artifact release must cover the current findings, and any eligibility approval used for a held artifact must cite a release that also covers them. A prior non-quarantine eligibility approval is not silently converted into an approval of new findings. The constrained projection is applied during intake, quarantine decisions, eligibility decisions and restoration; governed evidence is invalidated when a new blocking finding is observed. Earlier finding and decision history is preserved. Passive-parser findings now use a content-derived `passive-v2` identifier that incorporates the category, parser, version and status instead of an index alone; new findings do not automatically inherit historical index-based IDs.

If an earlier release does not cover newly observed findings, safety decisions are disabled and the queue calls for a governed review-history migration. An earlier eligibility approval that cannot be linked to a release covering the current findings remains blocked, even after a safety release. The current decision-chain rules do not provide a general migration or reapproval workflow; no new authority is invented. Cases with inconsistent pre-existing saved finding history can fail restoration rather than infer missing findings.

A same-session lock excludes intake, case switching and other safety/eligibility decisions while one of those two review operations is in progress. The lock is not a cross-window transaction, cannot cancel a hung workspace operation, and does not serialize unrelated review operations that were already in flight. Existing app review state, local actor names and hashes do not authenticate a reviewer or guarantee that all possible findings were captured. Partial writes and concurrent edits in other windows remain possible and require a governed operational policy. This change does not alter the DOCX MIME mismatch policy or approve real-data use.

## Validation

Synthetic tests exercised a previously approved text file re-submitted under a script-capable filename, the blocked eligibility after release and after reopening, newly observed findings after a prior release, and the same-session intake/case-switch lock. The prior same-finding quarantine inheritance flow remains tested. Tests used the development origin and a built `file://` origin with HTTP blocked and an in-memory workspace; they do not establish native office filesystem or security behavior. Typecheck, lint, format, schema and contract checks passed; an isolated single-file build and verification passed. The full automated suite passed 1,212 tests in 158 files with the approved local Data Dictionary. No real participant data, external actuarial execution or human approval was used.
